Hiroshi does not run a command inside the window.

A detached local daemon — the engine — owns every run. The cockpit is a client
of that daemon: it sends commands, follows one event feed and draws what it is
told. Close the window while a command is running and the command finishes.
Open a second window and it attaches to the same runs, mid-flight.

```
cockpit (React)  ──HTTP──▶  hiroshi-engine (bun)  ──▶  SQLite (engine.db)
        ▲                        │
        └──────── SSE ───────────┘
```

## What the engine owns

| concept | what it is |
| :--- | :--- |
| session | a workspace, a title, the messages sent in it and the runs started in it |
| prompt | an admitted intent: waiting in the inbox, or delivered as a message |
| message | a line of operator intent, recorded before anything acts on it |
| run | one command: its shell, its output, its exit code, its end |
| event | the append-only log every projection is built from |

The cockpit keeps no state of its own that the engine does not have. A fresh
window hydrates from one snapshot and then follows the feed from the
watermark that snapshot carried, so there is no gap and no double-draw.

## Durability

A run is written down before it has any effect:

1. The `run.started` event is committed **before** the shell is spawned.
2. Output is batched into `run.output` events, so a burst of lines costs one
   transaction rather than one per line.
3. `run.ended` records the exit code, the duration and the truncation flag.

If the machine dies in the middle of a run, the next start finds the run still
marked `running` and settles it as `interrupted`, with a final output line that
says the run was not resumed. A daemon never silently forgets work, and never
pretends a dead run is still going.

Output is bounded. A run that prints megabytes does not fill the database: the
engine keeps the first and last slices and marks the run truncated.

## The session inbox

A prompt is not a message yet when it arrives. It is admitted to the session's
inbox first, as its own durable fact (`prompt.admitted`), and delivered to the
transcript later (`prompt.delivered`) when the engine reaches a safe boundary.
That ordering is what makes steering possible: the client can keep talking
while a command is going, and the prompt is on disk before anything can act on
it.

- **Admission is idempotent.** A client sends a `key` with each prompt. The
  first admission wins; a retry with the same key returns the same item,
  whether it is still waiting or already delivered, and never turns into a
  second prompt.
- **Two modes.** `steer` and `queue`. Both wait while a run is executing; at
  the boundary every steer is delivered before anything queued, each in
  admission order. A steer does not stop the run it is steered past: it lands
  after the step that was already going.
- **A boundary is a step ending.** Today the engine's only step is a run, so
  the boundary is `run.ended` and the session is idle when no run is executing.
  When a step grows tool calls of its own, the boundary moves inside the step
  and the law does not change: nothing is delivered while a tool call is in
  flight.
- **An interrupt stops the runs, not the queue.** `POST
  /v1/sessions/:id/interrupt` writes a `cancelled` ending for every run the
  session holds, with a line carrying the operator's reason, and the queue is
  left as it was. The ending is a boundary, so whatever was waiting is
  delivered immediately after it.
- **A crash does not strand the queue.** On startup the engine settles the runs
  a dead process left behind, then delivers the pending inbox: a prompt
  admitted before the crash is in the transcript instead of waiting for a
  boundary that will never come.

`GET /v1/sessions/:id` carries the pending `inbox`, so a fresh window knows
what is waiting before it follows the feed.

## The wire

- **HTTP** on loopback, one JSON response per request, typed errors with a
  stable `code`.
- **One SSE feed** (`/v1/events`) that replays from a sequence number and then
  follows. Every event carries its `seq`; a client that reconnects asks for
  everything after the last one it applied.
- **One shape module** (`engine/src/protocol.ts`): the shapes, the event union
  and the operations table. The daemon routes on the table and the cockpit's
  client is built from it, so a command cannot exist on one side of the wire
  and not the other, and no client hand writes a path or a `fetch`.
- **One event union**: `EventPayloads` maps every event type to its body, so a
  subscriber sees the payload without a cast and the store refuses to record an
  event whose body does not belong to its type.
- **A bearer token** minted per daemon start, compared in constant time. It
  lives in the discovery file with owner-only permissions, and it never leaves
  the machine.
- **A protocol version** in the handshake. A cockpit that speaks another
  protocol reports the mismatch and leaves the daemon alone: it may be running
  commands for someone else.

## The feed

The feed is one hub, not one subscription per window. The engine encodes an
event once, as it is recorded, and hands the same bytes to every connection: a
second window costs a pointer, not a `JSON.stringify`.

Each connection has its own queue, and the queue has a capacity. A window that
stops reading fills its queue and is closed with an `overflow` frame that names
the reason; the run, the other windows and the order they see never change. The
client knows the last sequence it applied, so it reconnects from there.

Every connection opens with a `hello` frame carrying `lastSeq`, the durable edge
at that moment. The feed replays from the client's watermark to that edge, one
page at a time as the socket asks for a frame, then follows live. The connection
joins the live fan-out *before* the watermark is read, and on the daemon's single
thread nothing can be recorded in between, so an event is either in the replay
or on the live feed: never both, never neither. A `lastSeq` **behind** the
watermark the client asked from means the log lost ground (a different
database), and the client takes a fresh snapshot instead of waiting for events
that cannot come.

An idle connection gets a comment heartbeat every fifteen seconds, so a proxy or
a sleeping laptop does not silently turn a live feed into a dead one.

## The data directory

| platform | directory |
| :--- | :--- |
| Windows | `%LOCALAPPDATA%\Hiroshi` |
| macOS | `~/Library/Application Support/Hiroshi` |
| Linux | `$XDG_STATE_HOME/hiroshi`, else `~/.local/state/hiroshi` |

`HIROSHI_HOME` overrides it. Inside:

| file | what it is |
| :--- | :--- |
| `engine.db` | the event log and the projections, in SQLite |
| `engine.json` | the discovery file: url, pid, token, protocol, version |
| `engine.lock` | who is starting a daemon right now |
| `logs/engine.log` | the daemon's own log, including why it refused to start |

## Lifecycle

The cockpit never kills a daemon it did not need to kill.

- **Start**: the cockpit reads `engine.json`. If it is missing or stale, it
  spawns the engine detached, with no pipes back to the window, and waits for
  the file to appear.
- **Adopt**: two windows starting at the same moment race for a startup lock.
  The loser finds the winner's registry and attaches instead of starting a
  second daemon.
- **Restart**: the daemon settings page stops the process and starts a new one.
  That is the only place the cockpit asks a daemon to exit.
- **Crash**: a killed daemon leaves its registry behind. The next start reports
  the stale pid, discards it and takes over the same database.

## The CLI

The same binary the cockpit spawns is usable on its own:

```bash
bun engine/src/index.ts serve    # start in the foreground
bun engine/src/index.ts status   # what is running, on which port, since when
bun engine/src/index.ts stop     # ask it to shut down
bun engine/src/index.ts version  # engine version and protocol
```

`serve` is the default, so `bun run engine` starts the daemon. The cockpit
looks for a standalone `hiroshi-engine` binary next to itself before it falls
back to the checkout, which is how a packaged build runs without `bun`.

## In the cockpit

The right panel's **Terminal** surface is the engine's, not a mock: a command
there becomes a run, its output arrives on the feed, and the composer shows the
real exit code. Below it is the session's inbox: what was admitted and is still
waiting, with its mode, a `STEER`/`QUEUE` switch and an interrupt action while a
run is going. The chat transcript on the demo workspace is not engine-backed;
the terminal is the surface that shows the inbox today. The **Daemon** settings
page shows the process, the protocol, the database and the session count, with
the one button that restarts it.

## Tests

The engine has its own suite, because it does not need a GPU, a window or a
test renderer:

```bash
bun run test:engine
```

Those tests spawn real daemons on throwaway data directories and then try to
break the promise: they close the client, attach a second one, and kill the
daemon in the middle of a run. One of them starts the engine from a separate
launcher process that exits immediately, and then asks the engine to run a
command — the check that a run outlives the window.
